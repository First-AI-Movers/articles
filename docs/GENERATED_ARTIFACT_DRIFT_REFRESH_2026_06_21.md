# Generated-Artifact Drift Refresh + Date-Normalized Advisory Check (2026-06-21)

**Lane:** Maintenance / CI hygiene · **Scope:** the advisory `Generated artifacts` (`generated-artifacts.yml` → `tools/check_generated_artifacts.py`) check + a one-time artifact refresh.

Removes a recurring **false failure**: the advisory generated-artifact drift check compares committed artifacts byte-for-byte against a fresh `rebuild_local.py` regeneration, so a **build-date-only** change (no content change) registered as drift and failed the check on every docs/maintenance PR that ran the heavy path.

## What drifted

`rebuild_local.py` stamps `date.today()` into these **generation-timestamp** fields; on any rebuild landing on a later calendar day they changed `2026-06-06 → 2026-06-21` with **no content change**:

| Artifact | Field | Kind |
|---|---|---|
| `index.json` | `"last_updated"` | generation timestamp |
| `README.md` | `"dateModified"` | generation timestamp |
| `llms-index.txt` / `llms-recent.txt` / `llms-full.txt` | `- Generated:` footer | generation timestamp |
| `sitemap.xml` | `<lastmod>` of the **static aggregate pages** (`/`, `/about/`, `/topics/`) | generation timestamp |

These were the only diffs (8 lines across 6 files; `git diff` confirmed date-only — no content churn).

## What was done

1. **Date-normalized the advisory check.** `tools/check_generated_artifacts.py` now normalizes the generation-timestamp fields above (replacing the `YYYY-MM-DD` with a placeholder) on **both** the committed and the freshly-regenerated bytes before comparing. A build-date-only diff no longer registers as drift.
2. **One-time refresh** of the six committed artifacts (regenerated with the canonical `rebuild_local.py` + `update_docs.py`; date stamps now `2026-06-21`).
3. **Tests** (`tools/tests/test_check_generated_artifacts.py::TestNormalizeGenerationDates`, 6 cases): the four generation-timestamp fields normalize-equal across a date change; **content dates are NOT normalized** (a topic-hub `<lastmod>` and an article `published_date` still differ → real freshness change still fails). The 9 existing drift-detection tests still pass (15 total).

## What stays EXACT (content dates — must still fail the check)

- **Per-article / per-topic `sitemap.xml` `<lastmod>`** — the topic hub's newest-article date (`build_sitemap` uses `topic_max_dates.get(topic)`), e.g. `/topics/ai-agents/` = `2026-04-24` (unchanged).
- **`feed.xml` / `feed.json` dates** (`feed_updated` = the newest article's `published_date`; per-entry `pubDate`/`date_published`).
- Any human-authored / source date. The normalization is scoped to the four generation-timestamp fields only.

## Risk / scope

- **Advisory-only behaviour preserved** — `generated-artifacts.yml` is non-required (push:main + PR + dispatch; the safe-maintenance allowlist + heavy path are unchanged). No workflow/ruleset/required-check change.
- **Public repo only** (`articles`); no private-repo, billing, settings, or secret access; no manual deploy. (Run while private-repo Actions are blocked on org billing.)
- The `_SITEMAP_STATIC_LOCS` set mirrors `build_sitemap()`'s static pages and is documented to be kept in sync; a test covers the static-vs-content distinction.

## Follow-up

- If `rebuild_local.build_sitemap()` adds a new static (build-date-stamped) page, add its loc to `_SITEMAP_STATIC_LOCS`.
- The post-merge `build-and-deploy` Pages workflow runs on its own; this change does not deploy.
